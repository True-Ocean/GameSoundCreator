## 1. 当面のゴール（二軸）

音の印象は次の **2軸** で上げる。片方だけでは足りない。

| 軸 | ねらい | 主担当 Step |
|----|--------|-------------|
| **A. 音色・空間** | 乾いたチップチューン一色から、レトロコンソール〜初期インディーのシンセ曲へ | 3.5-C / 3.5-D |
| **B. 作曲・メロディ** | グリッド上のランダム音符から、覚えられるフレーズがある曲へ | **3.5-M**（本ドキュメントで定義） |

### 目指すもの

- **レトロゲームの BGM として違和感なく仮置きできる**
- ループが小節頭で自然につながる
- 雰囲気・音色の差が耳で分かる
- **別パターンで、リズム型やフレーズの型が違う**と感じられる
- 完全ローカル・手続き生成・外部AIなし

### 目指さないもの（今はやらない）

- 映画級オーケストラ／商用サンプル並みのリアルさ
- クラウド生成AI・大規模オンデバイス ML
- 人間作曲家の代替としての「名曲」保証
- 極端なグルーヴずれ（レトロ寄りではリズム型の方が効く）

### 品質段階（目安）

| 段階 | 内容 | 状態 |
|------|------|------|
| 出発点 | 単純波形＋制約付きランダムメロディ | 過去 |
| いま | 音色7種・フィルタ・短い残響・簡易FM **＋** モチーフ型メロディ | **Phase 3.5 のコア実装済み** |
| **ゴール（当面）** | 自作ゲームへ仮配置して、用途差・ループ・生成時間を実機で評価 | **Phase 4 の初期評価** |
| 将来 | サンプル同梱・ジャンル別作曲ルールの厚み | Phase 6 以降 |

## 2. 音色イメージ方針

ウィザード／スタジオの **「音色イメージ」**（BGM優先。SEは後続）。

### 実装済み

| ID | 表示名 | 用途 |
|----|--------|------|
| `lead_synth` | シンセリード | 戦闘・勝利ファンファーレ |
| `piano` | ピアノ | タイトル・メニュー・パズル（専用ボイス） |
| `pad` | パッド | 設定・休憩・敗北の床 |
| `bass` | ベース | 低音主役。探索既定 |
| `music_box` | オルゴール | ショップ・ガチャ（中高域ティン） |
| `organ` | オルガン | ストーリー・荘厳 |
| `guitar` | ギター | 冒険・町／拠点 |

### 直後に足す候補（任意・追加）

| ID（案） | 表示名 | 用途 |
|----------|--------|------|
| `flute` | フルート／笛 | 探索・町 |
| `bell` | ベル（オルゴール以外） | 短いファンファーレ寄り |

## 3. 合成エンジンの強化項目（音色軸）

1. **楽器エンベロープ** — ✅ 基本実装済み  
2. **フィルタ** — ✅ ワンポールLPF（雰囲気・音色でカットオフ）  
3. **短い残響** — ✅ 円形アーリーリフレクション＋軽いコム（ループ整合）  
4. **簡易FM** — ✅ 2オペレータ位相変調（音色別 ratio/index）  
5. **レイヤー割当** — ✅ 楽器ごとにドラム／ベース／コード／リードの役割・音量を整理  

ドラムは現行の合成キック／スネア／ハットを基本とし、生ドラム化は急がない。

## 4. 作曲エンジンの強化項目（メロディ軸）

### 4.1 解消した出発点の課題

Phase 3.5-M1 より前の `BGMEngine` のメロディは、おおよそ次の方式だった。

- 8分音符グリッド固定
- 現在コード付近の度数を **ステップごとに独立ランダム**
- モチーフ・フレーズ・問い／答え・休符設計なし

そのため **別パターン（seed変更）でも「同じルールのランダム」** に聞こえやすかった。現在は `MelodyComposer` がモチーフ・リズム型・輪郭を先に構成し、`BGMEngine` がそのノート列を参照する。

### 4.2 目指す「人間らしさ」（定義）

本プロジェクトでの「人間らしい」は次を指す（主観的な芸術性ではない）。

| 要素 | 意味 | 聴感の目安 |
|------|------|------------|
| **モチーフ** | 2〜4小節の短い形を先に決め、繰り返す／少し変える | 覚えられる塊がある |
| **リズム型** | 数パターンのリズム骨格から選ぶ（休符・シンコペ含む） | 別パターンでノリが違う |
| **音高輪郭** | 上昇→頂点→下降、問い（上行）と答え（下行）など | ランダム跳躍感が減る |
| **ハーモニー適合** | 拍頭はコードトーン中心、あいだに経過音 | 「メロディ」に聞こえる |
| **抑揚** | フレーズ頭をやや長く／強く、終わりを短く | 機械連打感が減る |

### 4.3 やらないこと（作曲軸・当面）

- UIに「作曲モード」や専門パラメータを増やさない（既存の seed／雰囲気／密度で効かせる）
- 大規模シーケンス言語や外部MIDIライブラリ必須化
- ボーカル・対位法の本格実装

### 4.4 実装イメージ（エンジン内部）

現行のデータ流れ（UI変更は最小）:

```
seed + mood + density + key + progression
        │
        ▼
  MelodyComposer（純ロジック）
        │  モチーフ度数列・リズムマスク・輪郭を生成
        ▼
  BGMEngine がステップ再生時に参照
```

- `MelodyComposer` は `AudioGenCore` 内のテスト可能な純関数／構造体とする
- 出力は「小節×ステップのノート列」（MIDI度数 or 相対度数＋長さ＋強さ）
- seed を変えれば **モチーフ家族やリズム型が切り替わる**ようにする（単なる同じ型の別乱数にしない）

### 4.5 第一弾の完了条件（3.5-M1）

- [x] 戦闘／メニューで、メロディに **2〜4小節の反復感**がある
- [x] 別パターンで **リズム型または輪郭の差**が耳で分かる（コード進行だけの差ではない）
- [x] 既存のループクロスフェード・生成時間の目安を壊さない
- [x] ユニットテストで、同一 seed なら同一ノート列になる

### 4.6 第二弾以降（バックログ・3.5-M2+）

優先はフィードバック次第。

| 項目 | 内容 |
|------|------|
| コール＆レスポンス | 2小節問い＋2小節答え |
| フィル小節 | 4小節目だけリズム／音域を変える |
| シーン別モチーフ辞書 | ✅ 雰囲気別辞書＋戦闘／メニュー並び偏り（3.5-M1b） |
| ベースとの役割分担 | メロディが忙しいときベースを単純化、など |
| ごく短いアーティキュレーション差 | スタッカート／テヌートの型 |

## 6. プロダクト上の位置づけ

```
Phase 0–3     土台（生成・UI・ループ・雰囲気）
Phase 3.5     音色・空間 ＋ 人間らしいメロディ作曲  ← コア実装済み
Phase 4       ピクセルバトルへ投入・実利用評価  ← 次の注力
Phase 5       App Store 販売準備
Phase 6+      ジャンル拡充・サンプル・作曲ルール厚み・バッチ書き出し等
```

音数が足りない・用途が少ない問題は、Phase 3.5 と並行／直後に **ピクセルバトル必須イベントから** カタログを増やす（全部を先に埋めない）。

## 7. 成功指標（Phase 3.5 完了）

### 音色・空間

- [x] 音色4種以上を選ぶと、同じシーンでも聴感が大きく違う
- [x] 「8ビットそのもの」ではなく、レトロコンソール〜初期インディー寄りの印象になる
- [x] フィルタ／短い残響がオンでも、ループ継ぎ目が破綻しない（円形処理＋クロスフェード）

### 作曲・メロディ

- [x] メロディに覚えられる短い塊（モチーフ）がある
- [x] 別パターンでリズム型またはフレーズ輪郭の差が分かる
- [x] 拍頭中心がコードトーン寄りで、単なるノイズ的跳躍に聞こえない

### 運用

- [ ] 生成時間が実機で許容内（目安: 数十秒ループが数秒以内）
- [ ] ピクセルバトル担当者が「仮置きして遊べる」と判断できる
